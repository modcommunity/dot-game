# Avatar actions

Emotes, poses and gestures: the server checks a request and tells everybody, and each client plays the clip on that player's figure.

`DotGameAvatarActionMessage` (BOTH directions, reliable, not required so an old client still connects) carries the action id; the server's reply adds the actor and the start tick. `DotGameNetcode.build` serves it through `DotGameAvatarActionRelay.serve`, which drops an id the player has not equipped (the starter 13 when the game has no `_avatar_actions_equipped(peer)`), a request faster than `min_interval_sec`, and anything the game's `_avatar_action_veto(peer, id)` refuses.

On the client, `DotGameClient.add_avatar_actions(net, figure_fn, backbone_actions = null)` builds `DotGameAvatarActionClient`: it sends a key press from dot-user-avatar's `DotAvatarActionInput` and plays a relayed start on `figure_fn(actor)` with `DotHumanoidFigure.play_action`, joining the clip late by the tick difference. dot-user-avatar and dot-player-char are reached by path and duck typing, never named. The client's settings node gets the three key rows (`DotMenuSettings.avatar_actions`).

Each game's client bridge must call `DotGameAvatarActionMessage.register(net)` before the schema seals, as the server does; a game that has not does not see the actions. Test: the "avatar actions" section of `examples/game_selftest.tscn`.

Files a server requires: the module's `_avatar_content_required()` (content ids, default none) is published as the notify cvar `sv_avatar_content`, so it rides the server's query rules (`DotBrowserEntry.rules`). Before the client connects, the connecting code calls `await client.prepare_avatar_content(entry.rules, base_url, server_id)`: it holds the gate (`avatar_content`), downloads and verifies through dot-user-avatar's fetcher, and on failure leaves the gate held showing why, so the caller must not connect. The player's equipped actions come from `await client.read_avatar_actions(http, user_key, headers)`, passed as `add_avatar_actions`'s third argument.

## Other players' loadouts

A client cannot read another player's equipped actions (the backbone wants the server's token) and is never believed about its own, so the server reads them. `DotGameAvatarActionRelay.serve` builds `DotGameAvatarLoadouts` (a child of the manager, named `AvatarLoadouts`) and `DotGameModule` makes the roster follow it. On each join it reads `GET <integration endpoint>/user/<scoped_key>/avatar` with `Authorization: Bearer <integration token>`, the credential of the registry's `dot_backbone_client` (as dot-platform finds it; `base_url`/`token` override), and the key from the session's `scoped_key` claim (`key_fn` overrides). A 404, no credential, no key or a failed read leaves the player on the starter 13; nothing is fatal.

- **Checked before it is believed.** `DotGameAvatarLoadouts.parse` keeps a built-in only by a known id of its own kind, an upload only by a well-formed `action/<id>/<version>` content id with a clip name of 1 to 64 characters, at most 8 per kind, no duplicates; an empty kind gets that kind's starters, as the site does. The relay then refuses any id outside that list, and takes `loop` from the entry, not the request.
- **Bounded.** `DotGameAvatarLoadoutMessage` is server to client only (a client's copy is refused by dot-net), at most 24 entries of ids up to 32 and clips up to 64 characters. Reads run `max_concurrent` (2) at a time from a queue of at most 128; `refresh(peer)` reads again no more than every `refresh_min_sec` (30 s), and every player is read again each `auto_refresh_sec` (60, 0 is off) so a re-equip reaches the game; a re-read that changed nothing sends nothing.
- **Late joiners** get every loadout already read before their own read starts. A leaver is forgotten by the relay and broadcast as an empty loadout. A read that returns after its player left, or after a new player took the peer id, is dropped (a generation per peer).
- **No URLs on the wire.** The server relays ids, kind, loop and clip; a client resolves the file, size and sha256 from the site's public library (`DotGameAvatarContent.fetch_clip`, dot-user-avatar's fetcher and cache), so a hostile server cannot point clients at arbitrary files.
- **The client** (`DotGameAvatarActionClient`) keeps each peer's loadout, fetches uploaded clips as they arrive (`content_fn`, which `DotGameClient` sets to the library fetch; at most 64 scenes kept), and when `play_action` has no such clip it hands the scene to dot-player-char's `DotHumanoidFigure.add_action_scene` and plays again. The local keys are rebuilt from the relayed loadout with each upload's real file url from the site library (`url_fn`, set by `DotGameClient`), and again once the library is read; the server never names a url.
- **Wearables ride the same message.** The read's `wearables` rows become `wearable/<id>/<version>` ids (`DotGameAvatarLoadouts.parse_wearables`, one per slot, at most 7) in `DotGameAvatarLoadoutMessage.wearables`; the client takes slot, bone, offset, url and hash from the library row (`wearable_row_fn`, which `DotGameClient` sets) and hangs them on the figure's skeleton with dot-user-avatar's `DotAvatarWearables.apply` (`DotGameAvatarActionClient.wear`). A figure not drawn yet, or a library row not yet read, is retried; each id is fetched once. A figure with no `skeleton()` (a seated driver's proxy, a disguise) wears nothing.

A server that is not on `DotGameModule` (arena, g2gfast, playground) passes its dot-server and calls `DotGameAvatarActionRelay.serve(net, self, server)` before the schema seals, then `DotGameAvatarActionRelay.loadouts_of(net).add_peer(peer)` / `remove_peer(peer)` in its join and leave handlers (or passes a `DotGameRoster` as `serve`'s fourth argument). On the client the local player's keys are rebuilt from their own relayed loadout (`DotGameAvatarActionClient.apply_to_input`), so they match what the server accepts.

Extension points: `_avatar_actions_equipped(peer)` on the module still wins when it returns a list (null means "what the server read, else starters"), `_avatar_action_veto(peer, id)` refuses beyond that, and `fetch_fn(key) -> DotResult` replaces the HTTP read (a suite, or a game with its own store). Test: the "avatar loadouts" and "avatar loadout client" sections of the suite.

The shell does this for every game: `DotGamePrejoin` (`prepare(host, address)`) asks the address for its rules (dot-browser, by path), downloads what `sv_avatar_content` names under a temporary gate whose progress goes to `progress_fn` (the shell's loading screen), gives up after `timeout_sec` (20) and always lets the join go ahead; a failure is a `game.prejoin` warning and the figures fall back to the stock avatar. dot-server-deploy's `shell.gd` `_connect_to` calls it before it opens the link. `server_id` is 0 until the server advertises its site id.
